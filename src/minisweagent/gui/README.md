# SWE-Xplorer demo GUI

A localhost web app for running **SWE-X**plorer (`TreeSearchAgent`) on a local git repository and watching the search tree grow live.

```bash
python scripts/swe_xplorer.py            # or: python -m minisweagent.gui
```

The GUI opens `http://127.0.0.1:8765/`. It uses only the standard library (no Flask/FastAPI), and the frontend is bundled, so it works offline.

## Platforms
* **Windows:** commands run in Git for Windows' bash. WSL is not needed. `python3` inside bash is mapped to the Python running the GUI.
* **Linux / macOS:** the system `bash`.

## Chat
The left panel is a chat. Each message is a request for the selected repository.
* **Reasoning:** the executed steps stream live as a collapsible block, in the order the agent ran them (thought, command, output, value).
  * Markers show backtracks, iteration boundaries, cross-path reconciliation, solution augmentation and tournament voting.
  * Clicking a step selects it in the tree.
* **Response:** the reasoning of the winning submission. If that submission was generated by solution augmentation, the tournament judge's summary is used instead.
  * A *Changes* card shows the files and the diff.
* **Review:** every result waits for **Accept** or **Reject** before the next request, or turn on *Auto-accept results* under the chatbox.
  * *Accept* runs `git apply` of that request's own patch in your repo, after a `--check`. The patch is relative to your code when the request was made. A conflict with edits you made meanwhile is reported, not forced.
  * *Reject* applies nothing. In in-place mode it restores the working tree to where the request started.
* **Each request starts from your repository's current state**, including your manual edits and untracked files, like the first one. Before a follow-up, the sandbox is re-synced from your repo: your HEAD is fetched, then your uncommitted and untracked changes are copied and committed.
* **Follow-ups grow in the same tree, under the last accepted submission node.** This uses the agent's own mechanism: after a submission, `step()` calls `_create_pseudo_root()`, which attaches a new pseudo-root under the submission node. The subclass in `observer.py` adds what that path lacks:
  * the new instruction in the prompts, with accepted results and rejected attempts summarised;
  * fresh per-request search state (iterations, step and cost budget, terminating candidates);
  * a per-request root commit, so each request's patch is relative to its own starting code.
* *New chat* starts over. The transcript is saved in `session.json` and restored after a restart. If the server restarts, the next request starts a new tree.

## Git graph
The *Tree | Split | Git* switch above the tree shows the workspace repo as a VS Code-style git graph. SWE-Xplorer keeps its state in git, so the graph shows how the search actually works:
* **Commits:** one per edit node, labelled with the node's action. Sibling candidates branch from the same parent, and pruned ones are faded.
* **HEAD** moves as the search backtracks (`git checkout`).
* **Follow-ups:** each follow-up request starts from a commit of your repo's current state ("SWE-Xplorer: your codebase at request N").
* **Uncommitted changes:** after a submission, the winning state is restored onto the root as working-tree changes and shown as an uncommitted row.
* **Selection:** clicking a commit selects its node in the tree and opens the diff in a docked pane; selecting a tree node highlights its commit.

The graph starts from the commits referenced by tree nodes (`git log --stdin`), because the agent works on a detached HEAD and many commits are unreachable from refs. It uses `--no-optional-locks`, so it never takes the index lock while the agent runs git.

## What it does
1. **Config:** pick any YAML in `config/extra/` (e.g. `swebench_ts.yaml`, `sb_fast.yaml`, `sb_wo_*.yaml`) or open your own. The `agent`, `model`, `reward_model` and `environment` sections become editable forms generated from the file.
   * Agent fields that are missing from the YAML appear with their defaults.
   * Keys the agent class ignores are flagged as *unused*.
   * The YAML tab edits the raw file, and *Save as…* writes a new one.
2. **Keys:** stored in the browser's localStorage and passed to the local server as environment variables. The server keeps them in memory only.
3. **Repository:** by default the repo is `git clone`d into the runs folder (*sandbox*). The agent's `git checkout`, `git reset --hard` and `git clean -fd` never touch your repo. *Accept* applies a request's patch with `git apply` after a `--check`.
4. **Visualisation:**
   * Live tree: executed path, frontier, scoring, backtracks, reconciliation (merged nodes), pruning at iteration boundaries, augmented solutions, and the tournament winner.
   * The *explore → reconcile → prune → select* cycle indicator.
   * Pause / Step / Stop, and a replay slider.
   * Node details: reward breakdown, command, thought, observation.
5. **Outputs** (per chat, in the runs folder): `workspace/`, `session.json`, and for each request `turn-N/` with `config.yaml`, `task.md`, `run.tree.json`, `run.traj.json`, `patch.diff` (this request, relative to its starting code) and `run.log`. Any `*.tree.json` can be reopened in the viewer.

## Design notes
* `observer.py` subclasses `TreeSearchAgent` and only wraps its methods to report progress, so the search logic is unchanged.
  * Relevance scoring returns 0.0 immediately when `SENTENCE_TRANSFORMER_SERVER` is unset, which is what the original does after its retries.
  * NaN BM25 relevance (all files scoring equally) is replaced with 0.0.
* `environment.py`: `LocalBashEnvironment` plus workspace preparation.
  * `git config --global …` issued by the agent is rewritten to a repo-local config.
  * Timeouts use coreutils `timeout`, so child processes are killed too.
* Security: the server binds to 127.0.0.1, rejects non-localhost `Host` headers (DNS rebinding), and rejects POSTs from other origins.
